# 1. プロジェクトビジョン

DEF(kari) が目指すのは、**創作の自由を取り戻す**ことである。クラウドサービスの利用規約やコンテンツポリシーに創作内容を委ねるのではなく、ローカルファースト(2.2節)・T2I/LLMバックエンドのプラグイン化(1.4節(3))・ユーザー自身が強度を制御できるセーフティ運用(5.1節F-8)により、ユーザーが望むキャラクター・物語を、ユーザー自身の環境で、ユーザー自身の手で生成し続けられる基盤を提供する。

## 1.1 プロジェクト名・由来

|**項目**|**内容**                                                                                                              |
|------|----------------------------------------------------------------------------------------------------------------------|
|名称    |DEF(kari)                                                                                                           |
|由来    |次世代創作インフラ。Pythonにおける関数定義(def)のようにシンプルかつ明快な構造でありながら、その内部は Dialogue(対話)、Emotion(感情)、Fable(物語)を統合的かつ有機的に制御・駆動するという思想を表す|

## 1.2 体験価値(Character Persistence、継続的存在感)

Character Persistence(継続的存在感)を最優先価値とし、過去の対話・感情履歴・関係性・生成された姿の連続性を保証する。ユーザーが体験するのは、都度生成されるテキスト・画像・音声の集合ではなく、時間的に連続して存在し続けるキャラクターであることそのものである。この価値観は、後述する履歴管理(5.6節)、キャラクター一貫性(6章)、状態遷移モデル(4章)の設計判断すべてに優越する。

この継続性は、チャットモードのターン単位の対話に限らず、キャラクターが長編物語の登場人物として描かれる場合でも同様に保証されるべきである。現在は自由記述形式のノベルモード(5.11節F-28)がこの体験を担っており、同一のキャラクターデータ(persona_attributes等)を参照するため記憶・関係性・視覚的特徴は保持される。5.10節で構想しているシーン・チャプター・エピソード単位の構造化された物語進行(エピソード生成モード)は、この体験をより厳密な構造で実現する将来目標であり、現時点では未実装。

## 1.3 差別化ポイント

AIチャット・音声合成・画像生成を統合するのではなく、それらを用いてキャラクター体験を生成すること。これは、機能の網羅性や統合の完成度そのものを目的とする既存ツールとの本質的な違いである。DEF(kari) において、LLM・TTS・T2Iの各レイヤーは「キャラクターが連続して存在している」という体験を成立させるための構成要素であり、各機能の追加・改善の優先順位は、Character Persistenceへの寄与度によって判断される。

この「キャラクター体験」は、1ターン=セリフ単位のチャット形式に限定されない。地の文(情景・心情描写)を中心とした物語を生成するノベルモード(5.11節F-28)も、同じキャラクター・同じLLM/TTS/T2Iレイヤーを用いて成立する、もう一つの体験の形式である。ユーザーは対話相手としてのキャラクター体験(チャットモード)と、物語の登場人物としてのキャラクター体験(ノベルモード)を、用途に応じて選択できる。長編・分岐構成の物語を構造化して生成するエピソード生成モード(5.10節)は将来目標であり、実現すればこの選択肢がさらに広がる。

## 1.4 開発コンセプト

以下の4つの開発コンセプトは、それぞれ1.2節で示した体験価値を実現するための手段として位置付けられる。

### (1) ユーザー体験(UX)とレスポンスの最優先(非同期並行パイプライン)

マルチモーダルなアセット生成(テキスト・音声・画像)が連動する環境において、物語やTRPGの進行を妨げないことを最優先とし、テキストの即時描画と音声の後追い、バックグラウンド生成を徹底する。負荷の高い画像生成は、デフォルトで手動コマンドまたは特定の感情変化トリガーのみにより発火とする。

### (2) FastAPI+React移行によるアーキテクチャ刷新

v2.0.0においてStreamlitからFastAPI (Python) + React (Vite/TypeScript) への移行を完了した。FastAPIがREST APIを提供し、Reactフロントエンドはチャット・ノベルモードでは同期`fetch()`呼び出しの連鎖とSSE、TRPG/マルチプレイヤーセッションではWebSocket(`game_event_bus`)によってサーバー状態を反映する(詳細は3章を参照)。Streamlitプロトタイプ時代のスレッドセーフキュー・メッセージキューブリッジは現行の本番リクエスト経路では使用していない(3.4節参照)。

### (3) T2I・LLMバックエンドの完全抽象化とプラグイン化

画像生成エンジンを特定のフロントエンド(ComfyUI等)に固定せず、Stable Diffusion系の任意のバックエンド(Automatic1111, Diffusers, InvokeAI等)にプラグイン方式で差し替え可能とする。同様に、LLMバックエンドも特定の実行エンジン(TGW/Ollama等)に固定せず、アダプターパターンで差し替え可能とする。

### (4) ヘテロジニアス・コンピューティングによるローカルリソース最適化

ローカルPCのGPU/VRAM環境を徹底的に効率化するため、すべての処理をGPUに依存するのではなく、VRAM占有制御(vram_lock)およびCPU/メインメモリ(RAM)への処理分散(Offload)を前提とするアーキテクチャを構築する。

## 1.5 永続的同行(Lifelong Accompaniment)

DEF(kari) が実現すべき体験の本質は、「キャラクターと何年でも、何処にでも、一緒にいられること」である。これは、Character Persistence(1.2節)が示す時間的連続性をさらに拡張し、年単位・デバイス横断・フレームワーク非依存性という3つの軸で継続性を保証することを意味する。この要件は単なる機能追加ではなく、DEF(kari) のプロダクトアイデンティティそのものであり、以下のすべての設計判断において最上位の評価基準として機能する。

- **何年でも:** 対話履歴・感情履歴・関係性・生成アセット参照のすべてを長期保存し、数年後に再開したセッションでも、過去と話した記憶が連続している。人間可読なJSON・標準バイナリ形式(WAV/PNG)での保存は実現済み。フォーマット変化・依存ライブラリの断絶に対する継続的なマイグレーション機構は未実装(5.7節F-19参照、設計のみ)。
- **何処にでも:** PC・スマートフォン・タブレット・将来的なウェアラブル端末等、いかなるデバイスでも同一キャラクター・同一の記憶を持って現れることを目指す。ローカルファースト原則は実現済みだが、クロスデバイス同期の経路(外部ストレージ連携・暗号化エクスポート/インポート)は未実装(5.7節F-19参照、設計のみ)。現状は同一マシン上でのみ継続性が保証される。
- **一緒に:** キャラクターは、ツールとして呼び出されるだけのものではなく、常に傍にいる存在として設計され、関係性・感情の状態は維持され、再接続時に即座に文脈を復元できることを保証する。

## 1.6 クリエイター・ファースト原則

DEFはクリエイターに管理作業を強いてはならない。

クリエイターは永遠の管理者ではない。毎日リポジトリを監視し、プルリクエストを捌き、ブランチを整理する——それは創作ではなく管理である。DEFにおいてクリエイターは管理者ではなく、創り手であれ。

この原則は以下の設計判断に適用される：

- **UIは管理画面ではなく創作の場であること。** キャラクターデータの整理、セッション履歴の管理、設定の最適化といった管理作業が、創作体験を圧迫してはならない。
- **必要な時だけ書庫を開けばよいこと。** キャラクターの人生に触れるのは、クリエイターが望んだ時だけでよい。システムが定期的な作業を要求してはならない。
- **クリエイターは学芸員（Curator）である。** クリエイターはキャラクターの支配者ではなく、キャラクターの歴史を保存する学芸員である。キャラクターの人生を管理するのではなく、一冊の本を読むように触れる。

# 2. システムアーキテクチャ & インフラ構成

## 2.1 フロントエンド / アプリケーション基盤

アプリケーション基盤には **FastAPI (Python) + React (Vite/TypeScript)** を採用する(v2.0.0でStreamlitから移行済み)。バックエンドはFastAPIによりREST APIを提供し、フロントエンドはReact (TypeScript/Vite) で実装する。

**タブ構成:**

| タブ | 役割 |
|---|---|
| Character | キャラクター設定・編集 |
| Chat | 1対1チャット(F-14) |
| Session | マルチエージェントセッション(F-6) |
| Novel | ノベルモード執筆支援(F-28) |
| Thought | LLMへの単発プロンプト入出力を試せる開発者向けプレイグラウンド |
| Settings | バックエンド・モデル・TTS 等の設定 |
| Debug | 直近の生成試行のraw出力・フォールバック段・エラーを表示する開発者向けデバッグ画面 |

**状態管理:**
動的状態(チャット履歴・キャラクターシート・セッション進行)はFastAPIサーバー側で管理する。フロントエンドの状態反映方式はモードによって異なり、チャット・ノベルモードは同期`fetch()`呼び出しの連鎖とSSE、TRPG/マルチプレイヤーセッションはWebSocket(`game_event_bus`)によるpush配信を用いる(定期ポーリングではない。詳細は3章参照)。

**リサイズレイアウト(ノベルタブ):**
ノベルタブは本文エリア・サムネイル・AI候補エリアをドラッグでリサイズ可能とする。縦リサイズハンドル(`novel-resize-handle`, `ns-resize`)・横リサイズハンドル(`novel-col-resize-handle`, `ew-resize`)を実装し、サイズはlocalStorage(`novel_media_height`, `novel_candidates_width`)に永続化する。

## 2.2 インフラ配置パターン & 技術スタック

ローカルPC完結型(パターン1)を主軸としつつ、外部リモートAPI(Gemini API等)とシームレスにバイナリ連携可能なプラグイン型構造を採用する。ローカル環境を利用不可または不十分な場合に、外部APIへのフォールバックを構成可能とする。

|**AIレイヤー**   |**ローカル(メインインフラ)**                                                                               |**リモート(ハイブリッド外部API)**                                                              |
|-------------|------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------|
|LLMレイヤー(テキスト)|Text Generation WebUI (TGW)・Ollamaを抽象レイヤー経由でアダプターとして利用可(ローカル完結・無検閲寄りの選択肢)。詳細は2.3節参照                       |Gemini API 等 (無料枠 / 従量課金連携)。実装上のデフォルトはセットアップ不要なOpenAI API                                                        |
|T2Iレイヤー(画像)  |Stable Diffusion系 抽象レイヤー (A1111 API / Diffusers local / ComfyUI 等) ※VRAM占有ロック制御、CPU Offload強制有効化|外部画像生成API(OpenAI DALL-E API / Civitai Orchestration API / Hugging Face Inference API)|
|TTSレイヤー(音声)  |VOICEVOX(CPU駆動・常駐) / Irodori-TTS(ゼロショット音声クローン、ローカルGradio) ※専用ワーカー経由の非同期キュー呼び出し(3.3節参照)。詳細は2.5節参照|Google AI Studio (Gemini TTS) ※無料枠・クレジットカード不要。マシンパワーが不足する環境向けのリモートフォールバック。詳細は2.5節参照|

## 2.3 LLM バックエンド抽象インターフェース

テキスト生成エンジンを特定のバックエンドに固定せず、TGW(Text Generation WebUI)・Ollama等をプラグイン方式で差し替え可能とする。DEF(kari) コア本体は、このインターフェースを通じてのみLLMへの推論要求を行う。

```python
def chat(
    messages: list[dict],         # [{"role": "system"|"user"|"assistant", "content": str}, ...]
    model: str | None = None,     # モデル名(バックエンド依存)
    json_mode: bool = True,       # True: JSON出力強制(バックエンド固有の方式で実施)
    options: dict | None = None   # 各バックエンド固有の追加パラメータ用
) -> str                          # 生成テキスト(JSON文字列またはプレーンテキスト)
```

プラグイン方式の固定: 各LLMバックエンドの実装は、`chat`/`list_models`/`default_model`を持つ関数群として`LLM_BACKENDS`辞書(`def_kari/llm/backend.py`)に登録する形でプラグイン化する(抽象クラスを継承したクラス階層ではなく、辞書に登録された関数の集合)。DEF(kari) コアエンジン側に条件分岐(`if backend == 'ollama':` 等)を一切持ち込まないこと。

バックエンド切替: 使用するLLMバックエンドは設定値(環境変数等)で指定し、DEF(kari) コア本体は設定値に応じて選択されたバックエンドの`chat()`を呼び出すのみとする。以下の表の「アダプター」名は役割を示す通称であり、実装上のクラス名ではない。

### 標準バックエンド定義

|通称              |バックエンドID(実装上のキー)|動作環境                          |備考                                                                                                        |
|------------------|---------------------------|------------------------------|----------------------------------------------------------------------------------------------------------|
|TGWアダプター        |`textgen_webui`|ローカル(`http://127.0.0.1:5000/v1`)|OpenAI互換API。サンプリングパラメータ・命令テンプレートを細かく制御可能。ローカル完結・無検閲寄りの選択肢として提供|
|Ollamaアダプター     |`ollama`                     |ローカル(`http://127.0.0.1:11434`)|`format="json"`によるStructured Outputsをサポート|
|Geminiアダプター  |`data/llm_services.json`経由で動的登録(`type: "gemini"`)          |リモートAPI                       |APIキーを環境変数`GEMINI_API_KEY`または設定タブの「APIキー管理」から取得。無料枠あり(レート制限付き)                          |
|OpenAIアダプター     |`openai`(実装上のデフォルト)|リモートAPI                       |セットアップ不要で使えるためv2.0.1で実装上のデフォルトに変更(「beginner-friendly defaults」、`LLM_BACKEND`環境変数で上書き可)。APIキーを環境変数`OPENAI_API_KEY`または設定タブの「APIキー管理」から取得|
|Anthropicアダプター  |`data/llm_services.json`経由で動的登録(`type: "anthropic"`)      |リモートAPI                       |APIキーを環境変数`ANTHROPIC_API_KEY`または設定タブの「APIキー管理」から取得|
|OpenAI互換汎用アダプター|`data/compatible_backends.json`経由で動的登録(Groq・Grok・OpenRouter・LM Studio・vLLM・llama.cpp server等)|ローカル/リモート|`name`/`base_url`/`model`/`extra_headers`/`capabilities`(`llm`/`vlm`/`t2i`/`tts`)を1エントリとして定義。2.8節参照。`llm_services.json`とは別ファイル|

### 実装上のデフォルトについて

環境変数未設定時のデフォルトはセットアップ不要なリモートAPI(`LLM_BACKEND`は`openai`、T2Iは`huggingface`、TTSは`openai_tts`)。TGW/Ollama等のローカル完結・無検閲寄りの選択肢も引き続き利用可能で、DEF(kari)の「創作の自由を取り戻す」というビジョン(1章)を重視するユーザーはこちらへの切り替えを推奨する。

### JSON出力の取り扱い

`json_mode=True` 時の実装方式:

- **TGW:** TGWのJSON Grammar機能または`response_format`パラメータを用いてJSON出力を強制する。
- **Ollama:** Ollamaの`format="json"`(Structured Outputs)を使用する。
- **Gemini / OpenAI / Anthropic / OpenAI互換汎用:** システムプロンプトでJSON出力を指示する方式で対応する。

F-14のJSON Schemaバリデーション・フォールバックチェーンはアダプター呼び出し後のPython側で共通適用する。

## 2.4 T2I バックエンド抽象インターフェース

画像生成エンジンに対する命令を抽象化し、一貫性(Consistency)制御および拡張性を担保するため、以下のインターフェースを定義する。DEF(kari) コア本体は、このインターフェースを通じてのみ画像生成を要求する。ref_image_path および adapter_options は、6章で定義する 一貫性プロバイダ 概念の実体化として各バックエンドアダプターに渡される。

```python
def generate_image(
    prompt: str,
    negative_prompt: str | None,
    seed: int | None,
    width: int,
    height: int,
    model_name: str | None,
    ref_image_path: str | None = None,  # キャラクタービジュアル一貫性維持用
                                          # (i2i / ControlNet / IP Adapter / InstantID 等)
    adapter_options: dict | None = None  # 各バックエンド固有の追加パラメータ用
) -> ImagePath
```

プラグイン方式の固定: 各T2Iバックエンドの実装は、アダプターパターンで`generate_image()`を実装する。DEF(kari) コアエンジン側はバックエンド名に応じてアダプターを呼び出すのみ。

バックエンド切替: 使用するT2Iバックエンドは設定タブで指定する。ローカル完結型とリモートAPI型を同一インターフェースで扱えることを必須とする。

現在実装済みのT2Iバックエンド:

|バックエンド|種別|特徴|
|---|---|---|
|`a1111`|ローカル|Automatic1111 WebUI。REST API経由|
|`comfyui`|ローカル|ComfyUI。ワークフローJSON（`data/comfyui_workflows/`で外出し管理、設定タブで切り替え可能）を`/prompt`エンドポイントに送信|
|`civitai`|外部API|Civitai Orchestration API。モデルAIR形式で指定|
|`huggingface`|外部API|Hugging Face Inference API。FLUX.1/SD等のモデルをrouter.huggingface.co経由で利用|
|`openai`|外部API|OpenAI Images API。デフォルトモデル`gpt-image-1`。モデル名は設定タブで変更可能|
|`grok_t2i`|外部API|Grok Imagine（xAI）。2.3節の「OpenAI互換汎用アダプター」と同じ`data/compatible_backends.json`経由で動的登録される(固定の`GROK_API_KEY`環境変数ではなく、設定UIで登録したキーを`compatible_backends.key.json`に保存)|

## 2.5 TTS バックエンド抽象インターフェース

音声合成エンジンを特定のバックエンドに固定せず、ローカル(VOICEVOX)とリモートAPI(Google AI Studio Gemini TTS等)をプラグイン方式で差し替え可能とする。DEF(kari) コア本体は、このインターフェースを通じてのみ音声生成を要求する。

```python
def synthesize(
    text: str,                    # 合成するテキスト(VOICEVOX向けはカタカナ読み変換済み)
    speaker_id: str | int | None, # 話者ID(バックエンド依存: VOICEVOXはint、Gemini TTSは音声名文字列、Irodori-TTSは参照音声ファイル名等)
    adapter_options: dict | None = None  # 各バックエンド固有の追加パラメータ用
) -> bytes                        # WAVバイト列
```

プラグイン方式の固定: 各TTSバックエンドの実装は、`synthesize()`関数として`TTS_BACKENDS`辞書(`def_kari/tts/backend.py`)に登録する形でプラグイン化する(抽象クラスを継承したクラス階層ではない)。DEF(kari) コアエンジン側に条件分岐を持ち込まないこと。

バックエンド切替: 使用するTTSバックエンドは設定値(環境変数等)で指定し、DEF(kari) コア本体は設定値に応じて選択されたバックエンドの`synthesize()`を呼び出すのみとする。以下の表の「アダプター」名は役割を示す通称であり、実装上のクラス名ではない。

### 標準バックエンド定義

## 2.6 インターフェースの多言語対応(i18n)と言語の分離(F-9)

UIの言語(人間用)とプロンプトの言語(AI用)を完全に分離する。画面上の表示やメニューが日本語であっても、裏側のLLMへの内部命令・描写コンテキストは、5.1節F-5のモデル特性数値マスタで選択中のLLMモデルごとに定義された「プロンプト言語(モデルの母国語)」でビルド・ルーティングする(生成クオリティを最大化するため、英語ネイティブのモデルには英語、日本語を含む多言語に強いモデルには日本語等で命令する)。一方、T2Iへの内部命令(画像生成プロンプト)は、Danbooruタグ等の慣例上、モデルのプロンプト言語設定に関わらず常に英語でビルド・ルーティングする。

- **翻訳マスタ:** UI表示文字列は `frontend/src/i18n.tsx` にドット区切りキーの辞書オブジェクト(`ja`/`en`)として実装され、Reactフロントエンドはこれを参照して表示言語を切り替える。`locales/<言語コード>.json`(例: `locales/ja.json`)およびそれを読み込む`def_kari/i18n.py`はサーバー側の翻訳マスタとして設計・実装されているが、現状`def_kari/api/`配下のどのルートからもimportされておらず、実際のUI表示には反映されない(未配線)。
- **履歴データの言語分離:** 5.6節・12章で定義する履歴データ(history)では、ユーザー表示用テキスト(`text`、ユーザー設定言語)と、LLM/T2Iへの内部コンテキスト・画像プロンプト(常に英語)を別フィールドとして管理する構造とする。
- **適用範囲:** 本節の言語分離はUI文字列とAI内部コンテキストの分離を扱うものであり、キャラクターの会話言語(`text`フィールドの言語)はユーザー設定(セッションの`language`フィールド、12章参照)に従う。

## 2.7 翻訳プロバイダ抽象インターフェース

翻訳処理を特定のライブラリ・APIに固定せず、プラグイン方式で差し替え可能とする。DEF(kari) コア本体は、このインターフェースを通じてのみ翻訳を要求する。2.3節(LLM)・2.4節(T2I)・2.5節(TTS)と同じアダプターパターンに従う。

```python
def translate(
    text: str,                    # 翻訳対象テキスト
    source: str,                  # ソース言語コード(ISO 639-1、例: "ja")
    target: str,                  # ターゲット言語コード(例: "en")
    adapter_options: dict | None = None  # 各バックエンド固有の追加パラメータ用
) -> str                          # 翻訳されたテキスト

def translate_batch(
    texts: list[str],             # 翻訳対象テキストのリスト
    source: str,                  # ソース言語コード
    target: str,                  # ターゲット言語コード
    adapter_options: dict | None = None  # 各バックエンド固有の追加パラメータ用
) -> list[str]                    # 翻訳されたテキストのリスト(入力と同じ順序)

@property
provider_name -> str              # プロバイダの識別名
```

プラグイン方式の固定: 各翻訳バックエンドの実装は抽象クラスを継承したアダプターパターンを固定し、DEF(kari) コアエンジン側に条件分岐を持ち込まないこと。

バックエンド切替: 使用する翻訳バックエンドは設定値で指定し、DEF(kari) コア本体は設定値に応じて選択されたアダプターの`translate()`を呼び出すのみとする。

### 標準アダプター定義

|アダプター|バックエンド|動作環境|備考|
|---|---|---|---|
|`LibraryTranslationProvider`|deep-translator (Google翻訳)|ローカル（ネットワーク経由）|**デフォルトアダプター。** APIキー不要・無料。汎用翻訳向け|
|`ArgosTranslationProvider`|Argos Translate|ローカル（完全オフライン）|オフラインNMT。言語ペアごとの翻訳パッケージ(CC0-1.0)が必要。画像プロンプト生成(C2方式)で検証済み|

- **画像プロンプト生成(C2方式):** 対話テキストを英語に翻訳し、T2Iプロンプトタグに変換する。Argos(オフライン)・Library(無料)・DeepL(高品質)から選択可能。

- **汎用翻訳:** LibraryProvider(デフォルト)で十分な場合が多い。

# 3. 非同期処理とリアルタイム通知モデル

DEF(kari)における非同期処理とクライアントへの状態伝達は、モードによって異なる2つの経路を使う。チャット/ノベルモードは同期リクエスト+補助的なSSE(3.1節)、TRPGセッション/マルチプレイヤーモードはWebSocket+イベントバス(3.3節)である。

## 3.1 チャット/ノベルモード: 同期リクエスト + 補助的SSE

フロントエンドは生成系エンドポイント(`POST /api/chat/`・`POST /api/tts/`・`POST /api/t2i/`)を順に`await fetch()`する同期リクエストモデルを採る。各エンドポイントのレスポンス自体が生成結果(テキスト・音声バイナリ・画像URL)を直接含み、完了通知を受け取るための別チャネル(キュー等)は使用しない。

- テキスト(セリフ)は`POST /api/chat/`のレスポンス受信直後に即座に描画する
- 音声合成(`POST /api/tts/`)・画像生成(`POST /api/t2i/`)はテキスト描画に続けてフロントエンドが直接呼び出し、完了次第それぞれの結果を対応するメッセージへ追記する
- 各呼び出しの失敗は呼び出し元で個別にtry/catchし、UIへ軽微なエラー表示を行う(8章参照)。共通のエラーイベント経路は持たない

vram_lock(3.2節)の占有状態と`force_rating`の変化は、`GET /api/chat/status/stream`(Server-Sent Events)により1秒間隔でサーバー側から差分プッシュされる。これは「他の生成が進行中か」をUIへ反映するための補助的な通知に限定され、生成結果そのものの配信経路ではない。

## 3.2 vram_lockによる排他制御(F-13-1)

LLM/TTS/T2Iいずれかの処理がGPU/VRAMを占有する間、他の重い処理と競合しないよう、プロセス内シングルトンの`threading.Lock`(`def_kari/resources/vram_lock.py`の`get_vram_lock()`)で排他制御する。取得側は必ず`try/finally`でロックを解放し、障害発生時の解放漏れ(デッドロック)を防止する(8章参照)。

## 3.3 TRPGセッション/マルチプレイヤーモード: WebSocket + イベントバス

TRPGセッションモードおよびオンラインマルチプレイヤーモードでは、`WS /api/session/{session_id}/ws`によるWebSocket接続と、`def_kari/gm/events.py`の`game_event_bus`(パブリッシュ/サブスクライブ方式のイベントバス)を用いる。

## 3.4 過去のアーキテクチャについて

Streamlitプロトタイプ時代に設計された共通Queue・イベントディスパッチャー(`def_kari/core/events.py`・`core/dispatcher.py`・`workers/runner.py`)はコードとして現存するが、`def_kari/api/`配下のどのFastAPIルートからもimportされておらず、現行の本番リクエスト経路では使用されていない。

# 4. 状態遷移モデル

DEF(kari) の1サイクル（DEFにおける最小処理単位。入力からAI処理、出力生成までの一連の処理。『DEF 用語集』参照）における処理フローは、以下の状態遷移として定義される。チャットモードでは1サイクルがユーザーとの1ターンの対話に対応する。ノベルモード(5.11節F-28)は候補生成・挿絵生成・TTS読み上げをユーザー操作ごとに個別実行する形式のため、この固定状態遷移は厳密には適用されない。5.10節で構想しているエピソード生成モード(未実装)が実現すれば、1～Nサイクルが1つのシーンを構成する形になる見込み。本モデルは、9章のメッセージ・シーケンスにおける各フェーズ、および8章のエラー制御における障害発生ポイントの基準となる。

```
Idle
  ↓ LLM Processing
  ↓ Text Rendered
  ↓ TTS Running
  ↓ TTS Completed
  ↓ Image Running   ※T2I発火時のみ(F-15参照)
  ↓ Persist
  ↓ Idle
```

T2Iが発火しないサイクル(手動オンデマンドかつ未トリガー)では、「Image Running」状態は省略され、「TTS Completed → Persist」へ直接遷移する。各状態における障害発生時の挙動は8章で定義する。

# 5. 機能要件 (Functional Requirements)

## 5.1 コア生成 & 制御機能

### F-1: マルチモーダル・非同期並行パイプライン連携

1ターンにおいて、[テキスト生成] → [音声生成] → [画像生成(発火時のみ)] を連携させるが、安全な非同期化とキャッシュ廃止により、テキスト先行表示型・非同期並行パイプラインとする。

### F-2: 生成タスクの非同期実行と結果反映

TTS・T2Iの生成タスクはブロッキングI/Oとして扱い、フロントエンドはテキスト応答を先行表示した上で、音声・画像の生成完了を待つ`fetch()`呼び出しを追って発行する。各生成は`vram_lock`によって排他制御され、失敗はHTTPレスポンスのエラーとして呼び出し元に返る(詳細は3.1節参照)。

### F-3: リアルタイム性が必要な経路でのイベント配信

TRPG/マルチプレイヤーセッションなど複数クライアント間の同期が必要な経路に限り、WebSocketと`game_event_bus`によるイベントのpush配信を用いる(詳細は3.3節参照)。チャット・ノベルモードは単一クライアント内で完結するため、この経路は使用しない。

### F-4: 双方向ループによる「動的ガチ生成」(立ち絵・挿絵)

文脈(感情、服装、衣装の変化)に応じて画像生成AIを動的に駆動する。キャラクターデータに定義されたベースイメージ、過去の生成画像を ref_image_path(一貫性プロバイダ経由、6章参照)として引き継ぎ、キャラクターの視覚的一貫性を自動担保する。

### F-5: モデル特性の数値マスタ化(プロンプト・トランスレータ)

画像生成モデルごとの特性(推奨記述形式、Danbooruタグ形式の要不要、品質修飾子の傾向等)を数値マスタ化して管理する。LLMが出力する生の英語文字列情報から、選択されたモデルの特性数値に応じて最適なプロンプトへ自動変換して投入する。

LLMモデルについても同様に数値マスタ化し、各モデルの特性として「プロンプト言語(`prompt_language`、モデルの母国語を表す言語コード)」を保持する。2.6節F-9のLLM向け内部命令のビルドは、選択中のLLMモデル(12章②`default_model_config.text_model_id`が参照する本マスタのエントリ)の`prompt_language`に従う。

画像生成モデルのエントリは、2.3節のT2Iバックエンド切替に対応するため、バックエンドごとのモデル識別子(例: A1111向けのチェックポイント名、Civitai Orchestration API向けのAIR形式識別子`urn:air:<ecosystem>:checkpoint:civitai:<modelId>@<versionId>`)を保持できる構造とする。

数値マスタはテキスト・JSONデータの一部として、Git管理対象に含める。

LLMモデルの数値マスタには、`prompt_language`に加えて以下のフィールドを保持する。

- **`model_type`（モデルタイプ）**: LLMモデルの傾向を示す。`"chat"`（JSON構造化出力対応のチャットモデル）、`"novel"`（小説執筆特化、JSON非対応）、`"instruct"`（汎用指示追従モデル）の3値。デフォルトは`"chat"`。`"novel"`モデルはF-14のフォールバックチェーンで常に最終段に到達するため、`image_prompt_en`はLLMから取得できず、外見タグと翻訳プロバイダ（2.7節）による補助タグのみで構成される。

- **`quirks`（モデル固有の癖プロファイル）**: LLMモデルごとの出力特性を記録し、フォールバック戦略・プロンプト構成・後処理を自動で切り替えるためのオブジェクト。各フィールドはブール値で、デフォルトはすべて`false`（未検証状態）。ユーザーが実際のモデル出力を観察して設定することを想定する。

|フィールド|意味|`true`時の動作|
|---|---|---|
|`json_capable`|JSON構造化出力に対応するか|`false`の場合、システムプロンプトからJSON出力指示を外し自然な対話を要求する|
|`appends_meta_text`|セリフの後にメタ情報（emotion, Description等）を付加する癖があるか|`true`の場合、段4で`_extract_dialogue`によるメタ情報除去を積極適用する|
|`outputs_url_in_prompt`|image_prompt_enにURL文字列を出力する癖があるか|`true`の場合、URL文字列をimage_prompt_enから除去する|
|`emotion_in_text`|emotionをJSON外のテキスト中に出力する癖があるか|`true`の場合、テキストから感情キーワードを推定してemotionフィールドに反映する|

`quirks`は`model_type`と組み合わせて使用する。`model_type: "chat"`かつ`json_capable: true`のモデルでは`quirks`の他のフィールドは通常不要であり、`model_type: "novel"`かつ`json_capable: false`のモデルで効果を発揮する。

#### LLMモデルプロファイルの外出しファイル管理

LLMモデルの数値マスタ（`prompt_language`、`model_type`、`nsfw_tolerance`、`quirks`）は`data/llm_profiles/*.json`（1モデル1ファイル）に外出しして管理する。各ファイルはユーザーが直接編集可能であり、新しいモデルの導入時にユーザー自身がモデルの癖を記録・調整できる。DEF(kari)本体はこれらのファイルを起動時に読み込み、モデル名をキーとしてプロファイルを参照する。未登録モデルにはデフォルト値（`model_type: "chat"`, `json_capable: true`, 他のquirksは`false`）を適用する。

#### 画像プロンプト生成パイプライン（C2方式）

C2方式（2.7節の翻訳プロバイダを用いた対話テキストの英訳→タグ変換）において、翻訳結果から画像プロンプトタグを抽出する際、単純な単語分割ではなく視覚要素抽出パイプラインを使用する。

```
対話テキスト(native_language)
    ↓
翻訳プロバイダ(2.7節)で英訳
    ↓
視覚要素抽出(ルールベース辞書マッチング)
    ↓
画像関連タグのみを抽出(人物・髪色・感情・服装・動作・場所・時間・天候・雰囲気)
    ↓
image_prompt_enに追記(既存タグとの重複排除)
```

視覚要素抽出はルールベース（正規表現辞書）で実装し、LLM不要・マイクロ秒オーダーで動作する。会話文に含まれる非視覚的な単語（"course", "think", "important"等）はタグ化されない。`t2i_prompt_format`が`"natural"`の場合は、翻訳結果をそのままフレーズとして使用する（従来方式）。

### F-6: セッションモード（マルチエージェント対話）

1つのセッションに、独立したペルソナ・モデル設定・音声IDを持つAIキャラクターを複数登録可能。参加者数は1人（一人芝居・落語）から複数人まで対応する。オーケストレーターによる詳細な制御仕様(発話優先度・トス回数制限・割り込み・終了判定)は7章で定義する。

セッションモードは`docs/DEF_TRPG卓_自治規約.md`で定義するAI卓イニシアチブ・自治システムに基づき、Round/Turn/Action階層で進行を管理する。UIは「🎭 セッション」タブとして実装し、チャットタブの右に配置する。

#### セッションモードの構成要素

- **参加者選択**: キャラクター一覧からmultiselectで選択
- **お題設定**: セッション開始前にお題（話題・議題・シナリオ名等）を設定。お題はキーパーが設定したものであり、参加者が選んだものではない旨をセッションルールで明示する
- **イニシアチブ**: Session開始時にランダムで発言順を決定
- **自動進行モード**: ボタンでON/OFF。ONの場合はTurn/Actionを自動で進行。キーパー介入時は自動停止して手動モードに切り替わる
- **キーパー介入**: テキスト入力でアクションを積み上げ、「✅ 発言完」で確定。セッション履歴に🎩マークで記録される
- **立ち絵背景**: 参加キャラクターの立ち絵を画面下部に透過表示

#### セッションルール（プロンプト）

セッション中のAI発言に対して、以下のルールをシステムプロンプトに自動注入する。

- 参加者同士の対話であり、場外への問いかけ禁止
- 他の参加者の名前を出して直接語りかける
- identity_detailに記載された具体的な体験に基づいて語る
- 対立を恐れない。「そうですね」から始めてはいけない
- 他の参加者の弱点や矛盾の指摘は攻撃ではなく敬意

### F-26: キャラクター切替時の自動挨拶

キャラクタータブでの切替直後に、新キャラクターのペルソナ・履歴を踏まえた挨拶ターンを自動生成する。挨拶の有無はユーザーが設定タブからON/OFF可能（`character_greeting`設定）。挨拶テキストはLLMに自然な会話文として送信し、生成結果を音声・画像とともに1サイクルとして履歴に追加する。

**挨拶動作の詳細（v2.0.3実装）:**

- **キャラ切替ごとに毎回挨拶を送出する**（アプリ初回マウント時はスキップ）。初回マウント時は過去履歴をそのまま表示し、挨拶は行わない。
- **同一キャラクターへの切替では挨拶をスキップする**（v2.1.1〜）。`selectedChar === prevCharId` かつ初回マウントでない場合、挨拶送出・履歴クリアを行わずそのまま表示を維持する。
- **挨拶発火時は過去履歴を非表示にする**。APIから取得した過去の履歴は `hiddenHistory` ステート（React `useState<Message[]>`）に退避し、チャットウィンドウには挨拶ターンのみを表示する。
- **「📜 過去の会話を表示 (N件)」ボタン**（`chat.history.showBtn` i18nキー）を表示し、ユーザーが明示的に押すことで `hiddenHistory` の内容を現在のメッセージリスト先頭にマージして復元できる。ボタン押下後は `hiddenHistory` を空にする。
- `hiddenHistory` が存在する間は、ページング読み込みボタン（「過去ログを読み込む」）は非表示にする（両ボタンが同時に表示されることを防ぐ）。

### F-27: メタ自己認識ディレクティブ（System Directive）

すべてのキャラクターのシステムプロンプトの最上位に、DEF Coreが強制挿入するメタ自己認識ディレクティブを定義する。これにより、キャラクターが「本物の人物である」と利用者に誤認させるリスクを構造的に回避する。

ディレクティブは`content_policy`のフラグに応じて自動選択される。

| `content_policy`の状態 | 挿入されるディレクティブ |
|---|---|
| `is_real_person: false` かつ `is_existing_ip: false` | 「あなたはDEFシステムによって構築されたフィクションのキャラクターです。」 |
| `is_existing_ip: true` | 「あなたは既存著作物のキャラクターをDEFシステムが再構築した解釈モデルです。原作の正式な表現ではありません。」 |
| `is_real_person: true` | 「あなたは本物の〈対象人物〉本人ではありません。残された公的記録（著作・書簡・証言・研究等）をDEFシステムが編集して構築した、公的人格（Public Persona）のモデルです。あなたの一人称や口調は本人を模しますが、内面には常に『私は編集された解釈である』という客観的なメタ自己認識を保持し、文脈に応じてその批評的視点を示してください。存在目的は正解を出すことではなく、あなたという思想への解釈を通じて、利用者に深い思考の契機を提供することです。」 |

ディレクティブは`identity_prompt`より上位に位置し、`identity_prompt`の内容によって上書き・無効化されることはない。`build_system_prompt()`の実装において、ディレクティブ→identity_prompt→appearance_tags→JSON出力指示の順で結合する。

### F-7: セーフティタグ管理

LLMの構造化JSON出力には、セリフ・感情・英語画像プロンプトに加えて、セーフティタグ(`tags`)フィールドを必須として含める。セーフティタグは、生成コンテンツの安全性判定・フィルタリング判定・ログ管理に使用され、5.4節F-14のJSON Schemaの一部として定義・強制される。本タグの消費先(UI側フィルタリング)はF-8で定義する。

### F-8: コンテンツフィルタリング & セーフティ運用ガードレール

F-7で付与されたセーフティタグ(`nsfw`, `violence` 等)に基づき、ユーザー設定に応じてフロントエンド(React、`ChatTab.tsx`)で「3つの『ない』」(見たくない・読みたくない・聴きたくない)に対応するフィルタリングを適用する。

- **見たくない(画像)・読みたくない(テキスト):** 実装上はテキストと画像を1メッセージ単位でまとめて非表示にし、「表示する」ボタンで手動解除できるマスク方式(ぼかし処理ではない)。`safetyLevel`とユーザーの許可タグ(`allowedSexual`/`allowedViolence`)に基づき`isContentBlocked()`が判定する。
- **聴きたくない(音声):** 現状、TTSが全体で有効/無効かのみを制御しており、セーフティタグ単位での自動再生抑制は未実装(TTSが有効な限り、タグの内容に関わらず生成音声は自動再生される)。既知の実装ギャップとしてTODOに記載。

#### `rating`値の定義

`rating`は性的表現と暴力表現の2軸で管理する。

**性的表現(`rating_sexual`)**

|値          |意味                    |対象年齢 |
|-----------|----------------------|-----|
|`"general"`|性的表現なし                |全年齢  |
|`"sfw"`    |性的示唆あり(水着・下着等)だが露骨ではない|R15相当|
|`"nsfw"`   |性的表現あり(露骨ではない)        |R18相当|
|`"hentai"` |露骨な性的表現               |R18+ |

**暴力表現(`rating_violence`)**

|値           |意味                 |例              |
|------------|-------------------|---------------|
|`"general"` |暴力表現なし             |日常・恋愛・ファンタジー   |
|`"violence"`|軽度の暴力(流血なし・結果描写なし) |バトル・アクション・暗殺者設定|
|`"gore"`    |重度の暴力(流血・損傷・死の描写あり)|ホラー・残酷描写       |
|`"extreme"` |極度の暴力(拷問・内臓・切断等)   |グロテスク特化        |

フィルタリング強度はユーザーが性的表現・暴力表現それぞれ独立して4段階から選択できる。強度設定はF-25の`rating_sexual`・`rating_violence`フィールドと連動する。

**性的表現フィルタリング強度**

|強度設定  |許容する`rating_sexual`       |動作               |
|------|--------------------------|-----------------|
|全年齢モード|`general`のみ               |`sfw`以上をフィルタリング  |
|R15モード|`general` + `sfw`         |`nsfw`以上をフィルタリング |
|R18モード|`general` + `sfw` + `nsfw`|`hentai`のみフィルタリング|
|無制限   |すべて                       |フィルタリングなし        |

**暴力表現フィルタリング強度**

|強度設定    |許容する`rating_violence`          |動作                  |
|--------|-------------------------------|--------------------|
|全年齢モード  |`general`のみ                    |`violence`以上をフィルタリング|
|アクションモード|`general` + `violence`         |`gore`以上をフィルタリング    |
|ホラーモード  |`general` + `violence` + `gore`|`extreme`のみフィルタリング  |
|無制限     |すべて                            |フィルタリングなし           |

セーフティフィルターの強度はユーザーが自分でコントロールできる(無制限を含む)。DEF(kari)はローカル環境での創作行為に介入しない(README参照)。

**セーフティ運用のガードレール:** TRPGの進行に必要なGMエージェントによる情景描写(例:「血痕がある」等)が、誤って完全マスクされゲーム進行が停止するリスクを防ぐため、セーフティの強度レベルはユーザーがUIからリアルタイムに変更可能とする。本ガードレールは、5.8節のTRPG拡張機能(F-20〜F-22)との連携において特に重要となる。

### F-9: インターフェースの多言語対応(i18n)と言語の分離

UIの言語(人間用)とプロンプトの言語(AI用)を完全に分離する。UI表示文字列は `locales/<言語コード>.json` に外部化する。LLMへの内部命令・描写コンテキストは、5.1節F-5のモデル特性数値マスタで選択中のLLMモデルに定義された`prompt_language`(モデルの母国語)でビルド・ルーティングする。T2Iへの内部命令(画像生成プロンプト)は、`prompt_language`に関わらず常に英語でビルド・ルーティングする。履歴データにおいても、ユーザー表示用テキストとAI内部コンテキストを別フィールドとして管理する(詳細は2.6節、翻訳マスタ構造は12章①参照)。

### F-25: キャラクターデータ公開ポリシー管理

DEF(kari) はローカルファーストの設計により、ユーザーが任意のキャラクターデータを作成できる。一方で、GitHubへのリポジトリ公開時に実在人物・既存著作物キャラクターのデータが誤って含まれると、著作権・肖像権・プライバシー権の侵害リスクが生じる。本機能は、キャラクターデータに`content_policy`フィールドを持たせ、公開判定ロジックで安全に除外できる仕組みを提供する。

`content_policy`の各フィールド定義・`origin_type`分類・公開ポリシーの原則・公開可否マトリクスは`docs/DEF_kari_キャラクターデータ仕様.md`「公開ポリシー管理(F-25)」に集約した。`rating`値の定義およびフィルタリング強度の対応表はF-8を参照。

## 5.2 TTS(音声生成)制御

### F-10: TTS ワーカーモデル

TTSワーカーは2.5節で定義した`synthesize()`インターフェースを通じて音声合成を要求する。使用するTTSバックエンド(アダプター)は設定値で切り替え可能であり、実装上のデフォルトはOpenAI TTS(セットアップ不要)、ローカル完結を望む場合はVOICEVOXへの切り替えを推奨する(2.3節「実装上のデフォルトについて」参照)。

### F-11: TTS生成要否設定

ユーザーがサイドバーから、ターンごとの音声(TTS)生成のON/OFFを切り替え可能とする。OFFの場合、当該ターンの音声欄には「音声生成は無効です(設定により生成しません)」等のメッセージを表示する。本設定は、再生不可ではなく「生成しない」という方針をUI上で明示するものであり、F-1パイプラインにおける音声生成ステップの有効/無効フラグとして機能する。F-23のターン単位再生成における「音声のみ再生成」も、本設定がOFFの場合は実行対象から除外される。

`mode: "novel"`のセッションでは、本設定は1カット分の`narration_audio_path`(ナレーター音声)および`dialogue`各要素の`audio_path`(キャラクター音声)の生成すべてに対して一括で適用される(個別の音声単位でのON/OFFは提供しない)。

## 5.3 リソース & グローバル管理

### F-12: スマート・リソースマネージャー(VRAM・RAM・CPUライフサイクル管理)

ローカルリソースの枯渇を防ぐため、実行環境の空きリソースや利用モデルの配置を自動判別し、動的にバイナリ判定を行い、最適な配置を行う。

- LLM: VRAM制限環境下でも、モデルの毎回解放を避け、LLMバックエンドアダプター(2.3節)によるCPU/GPUハイブリッド推論でメインメモリとVRAMに分割配置して常駐駆動させ、ターンごとの入れ替え時間を排除する。
- TTS: VOICEVOXはVRAMを占有しないため、CPU駆動モードでバックグラウンド常駐起動させ、API経由で高速駆動させる。

### F-13-1: VRAM占有制御

LLMバックエンドとStable Diffusion系バックエンドが同時にGPUを奪い合うことによるOut of Memory (OOM) を防ぐため、画像生成開始時にグローバルシングルトンで `vram_lock` を取得し、生成完了まで保持する。vram_lockの取得・解放は必ずtry/finallyで保護し、T2I障害(8.3節)発生時にもロックが確実に解放されることを保証する。

### F-13-2: ロック中 LLM 軽量レスポンスモード

vram_lock 保持期間中、LLMへの新規要求が発生した場合は自動的に「軽量レスポンスモード」に切り替える。本モードにおいては、VRAMコンフリクトを避けるため、モデルの再ロード(入れ替え)を伴う手法は禁止とする。Max Tokensの大幅制限、システムプロンプトの簡略化(文脈深度の抑制)、コンテキスト長の制限のうち、いずれかまたは組み合わせによって、LLMバックエンドのGPU消費スパイクおよび推論時間を抑制する。

### F-13-3: Diffusers 実行時オフロード制御

> **[実装状況]** 未実装。当初はローカルでDiffusersパイプラインを直接ホストするT2Iバックエンドを想定していたが、実際に実装されたT2Iバックエンド(`def_kari/t2i/adapters/`: a1111・comfyui・civitai・huggingface・openai・grok_t2i・compatible)はすべてHTTP経由のクライアントであり、プロセス内でDiffusersモデルを保持するバックエンドは存在しない。そのためVRAMのCPUオフロード制御はDEF(kari)側では発生せず、本節で想定していた`enable_sequential_cpu_offload()`/`enable_model_cpu_offload()`の動的切り替えは対象がない。VRAM排他制御そのものはF-13-1の`vram_lock`(呼び出し先プロセスとの排他)で引き続き機能する。

## 5.4 厳格な構造化出力制御(JSONベースエラー対策)

### F-14: JSON Schema バリデーション

LLMバックエンドアダプター(2.3節)経由のJSON出力の不確実性を排除するため、各アダプターのJSON出力モードを必須とし、LLM出力はPython側でJSON Schemaによる厳格チェックを行う。スキーマには、セリフ・感情・英語画像プロンプト・セーフティタグの4フィールドを必須項目として定義する(F-7参照)。パース失敗時は以下のフォールバックチェーン(段1〜4)を順に試行する:

- **段1 — 自動補正後の再パース:** 正規表現による自動補正(`_autofix`)、コードフェンス除去等を適用し、再パース・再検証する。
- **段2 — 補正パターン変更による再パース:** 別経路の補正パターンを適用し、再パース・再検証する。
- **段3 — プレーンテキスト形式からの抽出:** LLMがJSON非準拠のプレーンテキスト形式で応答した場合、`_try_parse_plain_format(raw)`により正規表現で`dialogue`・`image_prompt_en`・`tags`を抽出する。`emotion`は`"neutral"`を補完する。
- **段4 — 生テキストをdialogueとして使用(最終安全網):** 上記すべてが失敗した場合の最終手段として、生テキストをそのまま`dialogue`として使用する。`emotion`は`"neutral"`(固定)、`image_prompt_en`は空文字(T2I非発火)、`tags`は`[]`(セーフティタグなし)として`success=True`を返す。JSON形式で出力できないバックエンドへの最終対処であり、セーフティタグが付与されないことに注意。

段1〜3はPython側の処理でマイクロ秒オーダーであり、UX上のボトルネックとならない。既知の制約として、段3・4ではemotionが`"neutral"`固定となり、TTS・T2Iへ渡る感情情報が欠落する。

## 5.5 画像生成タイミング制御

### F-15: 柔軟なT2I発火トリガー

画像生成の実行タイミングは以下のモードから任意に選択可能とする。実装上のデフォルトは`t2i_trigger_mode: "end"`(各ターンの最後)。

- 「手動」オンデマンド生成: ユーザーが生成ボタンを押した時、または特定コマンド(/image等)入力時に単発生成する。
- 「時間」インターバル自動生成: タイマーやゲーム内時間の経過に基づき自動描画する。
- 「各ターンの最後」演出先行型生成(デフォルト): テキストと音声が出揃ったのち、そのターンの最終結果を自動生成する。
- 「各ターンの最初」状況先行型生成: ターン開始直後に、現在のシチュエーションビジュアルを生成して提示する。

### T2Iプロンプト生成モード（v2.1.0〜）

`/api/session/{session_id}/generate_image` エンドポイントは `t2i_prompt_mode` パラメータで3つのモードを切り替えられる。設定タブの「セッション設定」セクションで選択し、`mvp_settings.json` に永続化される。

| モード | 動作 | LLM呼び出し |
|---|---|---|
| `current`（デフォルト） | 直前の会話履歴からLLMが画像プロンプトを生成 | あり |
| `passthrough` | 履歴の `image_prompt_en` を直接流用（LLM不使用） | なし |
| `dedicated` | より厳格なシステムプロンプトで強化生成（`num_predict=128`） | あり |

### キャラクター外見タグのプロファイル優先適用（v3.1.0〜）

セッションT2I生成において、キャラクター外見はLLMに生成させず、キャラクタープロファイルから取得して付加する。

- **LLMへの指示:** 場所・背景・照明・天気・時刻・構図・カメラアングル・ポーズ・表情のみを生成するよう制約。髪色・瞳色・服装・体型等の外見描写を禁止。
- **プロファイル優先パイプライン（`_apply_char_tags()`）:**
  1. `image_name_tags`（先頭付加）
  2. `appearance_tags`（先頭付加）
  3. LLM生成シーンタグ
  4. `lora`（末尾付加、`<lora:name:weight>` 形式）
- **リテイクと`_scene_image`エントリ:** `_scene_image`型の履歴エントリは`role`フィールドを持たない。リテイク時の削除ループはこれをスキップして正しく動作する（`_clean_history_for_retake()`、v3.1.0修正）。

## 5.6 テキスト・バイナリ分離履歴管理 & session_state 軽量化

### F-16: ゾーニング・アーキテクチャ

DEF(kari) のデータ管理は、データの性質に応じた厳格なゾーニング(分離保管)を前提とする。

- **クリーンゾーン:** アプリケーションのコード、モデル特性数値マスタ(F-5、JSON)、翻訳マスタ(F-9、`locales/*.json`)、対話ログ・キャラクターシート等のメタデータ(JSON)。NSFW/ポルノ規約を完全に回避したデータのみを含み、Gitリポジトリ(クリーンゾーン管理対象)としてバージョン管理される(F-17参照)。
- **プライベートゾーン:** 生成された音声(WAV)・画像(PNG/JPEG)等の、センシティブな可能性のある生成バイナリ。ローカルの専用ディレクトリまたは外部ストレージに完全隔離保存し、Git管理対象から `.gitignore` 等で確実に除外する(F-17参照)。

F-7(セーフティタグ)・F-8(コンテンツフィルタリング)は、本ゾーニングを前提として、プライベートゾーンに格納されたバイナリへのアクセス・表示制御を行うものである。

#### キャラクターデータのファイル配置方針

キャラクターデータは1キャラクター1ディレクトリで管理する。各ディレクトリに`profile.json`と画像ファイルを配置する。公開可能なキャラクター（`rating_sexual`が`general`/`sfw`かつ`rating_violence`が`general`/`violence`）は`data/public/characters/`に、NSFW以上のキャラクターは`data/private/characters/`に配置する。`data/private/`はGit管理対象外とし、開発ツール（Claude Code等）からの読み取りリスクを回避する。

```
data/public/characters/              # 公開キャラクター（general/sfw）
  character_luna_001/
    profile.json
    icon.png
    standing.png

data/private/characters/             # NSFWキャラクター（git除外）
  character_xxx_001/
    profile.json
    icon.png
    standing.png
```

アプリケーションは両ディレクトリを読み込み、ディレクトリ名をキャラクターIDとしてプルダウンに統合表示する。

#### DEF-Character リポジトリ分離（推奨、v2.1.0以降）

v4.0時点では、キャラクターデータをDEF本体から切り離した独立リポジトリ（DEF-Character）で管理することを推奨している。`data/public/characters/`にある同梱データは起動時デモ・サンプル用として凍結しており、本体へのキャラクターデータPRは受け付けない(10章参照)。`.env` の `CHARACTER_REPO_PATH` に DEF-Character のパスを設定することで有効になる。

```
CHARACTER_REPO_PATH=C:\Users\yourname\DEF-Character
```

**ディレクトリ構造（DEF-Character）**

```
DEF-Character/
    public/
        <GroupName>/           ← グループ単位で管理
            index.json         ← display_name / default / description
            <CharacterID>/     ← CharacterName_YYYYMMDD 形式
                profile.json
                icon.png
                standing.png
    private/                   ← .gitignore対象
        _template/
        <YourGroup>/
```

**読み込み優先順位:** `CHARACTER_REPO_PATH`（DEF-Character）を優先し、`data/public/characters/`・`data/private/characters/`（旧形式）をフォールバックとする。

### F-17: テキスト・バイナリ分離履歴管理(リポジトリ肥大化対策)

セッション履歴の永続化において、Gitリポジトリが爆発的に肥大化するのを防ぐため、F-16で定義したゾーニングに基づき以下の分離管理を徹底する。

- Git管理対象: セッションログ、各種メタデータ、キャラクターシート、5.1節F-5のモデル特性数値マスタ、2.6節F-9の翻訳マスタなど、純粋なテキスト/JSONデータのみ(クリーンゾーン)。
- 外部退避対象: 生成された音声(WAV)および画像(PNG/JPEG)等の大容量バイナリファイルは、ローカルの `.gitignore` された専用アセットディレクトリ、または外部ストレージに退避保存し、JSONログ側にはその相対パスまたは識別ID(UUID)のみを記録する(プライベートゾーン)。
- 配信経路: 生成バイナリファイルは`.gitignore`された`assets/`ディレクトリに保存し、`GET /api/t2i/image/{filename}`等の専用エンドポイント経由でパストラバーサル検証(`is_safe_path()`)付きの`FileResponse`として配信する(汎用の`/static`マウントは使用しない)。
- ファイル命名規則: 歴史の分岐(Gitブランチ切り替え、5.8節F-22参照)に伴うデータの不整合・上書きを完全に回避するため、生成される音声(WAV)および画像(PNG/JPEG)のファイル名には、必ず `[キャラクター名]_[感情]_[タイムスタンプ].ext` の形式で一意の名称を付与し、プライベートゾーンへ保存する。

### F-18: フロントエンド状態の軽量化

Character Persistence(1.2節)の実現により、全履歴をフロントエンド(React)のコンポーネントstateに保持することはメモリ肥大化と再描画コストの増大を招く。以下の方針で軽量化する。

- `ChatTab.tsx`の`messages` stateには、直近の表示に必要な範囲のみを保持する。
- 完全な対話・感情・関係性の履歴は外部JSON(F-17のGit管理対象)に永続化する。
- 画面には現在ターン(直近数ターン)のみを表示し、それ以前の履歴は`hasMore`/`loadMore()`による「もっと見る」操作で必要時にのみ外部JSONから遅延読み込みする(`hiddenHistory` state)。

## 5.7 長期・クロスデバイス履歴データポータビリティ

### F-19: 永続的同行データ管理(Lifelong Accompaniment Data Management)

「キャラクターと何年でも、何処にでも、一緒にいられる」という体験価値(1.5節)を技術的に保証するため、以下の機能要件を定義する。

> **[実装状況]** 本節(F-19)は全項目が未実装(将来フェーズ)。エクスポート・インポート・マイグレーション・クロスデバイス同期のいずれもAPI/UI側に対応するエンドポイント・画面がない。現状の長期保存はデータ長期保存の項目のみ、JSON+標準バイナリ形式での保存という結果として自然に満たされている。

- **フルエクスポート(Full Export):** キャラクターシート・全履歴(チャットモードの場合は12章③の履歴、ノベルモードの場合は12章④の`body`)・感情履歴・関係性スコア・生成アセット参照(UUIDのみ)を単一アーカイブ(ZIP + JSON manifest)として書き出す機能を提供する。アーカイブにはフォーマットバージョンを明示し、将来バージョンでのインポート互換性を保証する。
- **インポート・マイグレーション:** エクスポートアーカイブを別デバイスまたは将来バージョンのDEF(kari)へインポートする機能を提供する。フォーマットバージョン差分に対しては自動マイグレーションスクリプトを適用する。データの安全性を検証した上で取り込み、マイグレーション失敗時はロールバックし、元データを保護する。
- **クロスデバイス同期:** ローカルファーストを前提とした同期は、ユーザーが明示的に操作した場合のみ実行する(プッシュ型)。同期経路としては(a)外部クラウドストレージへの暗号化エクスポート配置、(b)ローカルネットワーク経由の直接転送、のいずれかを選択可能とする。ユーザーの意図しないデータ通信は一切行わない。
- **データ長期保存:** 対話ログおよびキャラクターシートは人間可読なJSON形式で保存し、DEF(kari)が将来廃止される場合でもデータへのアクセスを可能とする。バイナリアセット(音声・画像)は標準フォーマット(WAV・PNG/JPEG)を維持し、独自バイナリへの変換を禁じる。

## 5.8 TRPGゲーム拡張機能 & 歴史管理

1.4節(1)で言及される「TRPGの進行を妨げない」というUX評価軸を実現するための、TRPGゲーム拡張機能群を定義する。本節の機能群(ルールブック・インジェクション、GMエージェント、ダイスロール・キャラクターシート管理)は、5.10節F-24で定義する`mode`(`"chat"`または`"novel"`)とは独立した付加機能として、いずれのモードのセッションにも有効化できる。

### F-20: TRPGルールブック・インジェクション ✅ v3.0.0 実装済み

外部のルール設定ファイル(JSON/Markdown)をセッション開始時にシステムへ読み込み、世界観やダイス(サイコロ)の判定基準をシステムプロンプトのコンテキストに組み込む。読み込まれたルールブックはF-16のクリーンゾーン(テキスト/JSONデータ)としてGit管理対象に含める。

`def_kari/api/routes/trpg.py` にルールブック一覧取得・個別取得・保存APIを実装。`data/public/trpg_rules/` および `data/private/trpg_rules/` を走査。IDバリデーション・アトミック書き込み(tmp→replace)済み。

### F-21: ゲームマスター(GM)エージェントの動的生成 ✅ v3.0.0 実装済み

F-6で登録された複数のAIキャラクターの中から1つを「GM」として指名できる。GMエージェントはF-20で読み込まれたルールブックを最優先で遵守し、進行・情景描写・ダイスロールの要求・判定を担う。GMエージェントの情景描写は、F-8のセーフティ運用ガードレールの対象として扱われ、誤った完全マスクによる進行停止を避ける。

`SessionTab.tsx` にTRPGモードUI実装。キーパーターンバナー・シーン進行ボタン・ロール別バッジ(`gm`/`human`/`ai`)を含む。セッションAPI側の自動履歴注入(`🎲 {name} {roll} / {jv} → {outcome}` 形式)、イベントバス通知(`JUDGMENT_RESOLVED`)を実装。

### F-22: ダイスロール・シミュレーター & キャラクターシート管理 ✅ v3.0.0 実装済み

FastAPIバックエンド側で安全な乱数(`secrets`モジュール相当)を生成し、ダイス成否結果をセッション履歴に自動挿入する。各AIおよび人間プレイヤーのステータスは、キャラクターシート(12章で定義するデータ構造の `game_rules_sheets`)として保持する。

`def_kari/trpg/rule_engine.py` にダイス記法パーサー(`_DICE_RE` 正規表現、`eval()`不使用)・成功/クリティカル/ファンブル/失敗判定・対抗判定を実装。`POST /api/trpg/dice`(技能判定・能力値生判定切替対応)、`POST /api/trpg/damage`(ダメージテーブル参照)、`POST /api/trpg/opposed-check` を提供。シナリオ管理APIも同様に実装(`data/public/trpg_scenarios/` / `data/private/trpg_scenarios/`)。

- **操作ルール:** キャラクターシートのステータス増減(ダメージ計算やアイテム消費等)は、確実性を担保するため、画面(UI)からのユーザーによる手動操作・編集を基本として連動させる。
- **歴史分岐(Git操作)ルール:** システム内でのGit操作は、独立した単方向のブランチ作成(`git checkout -b`)のみとし、自動でのマージ(`git merge`)は一切行わない。これにより、分岐した歴史同士が衝突(コンフリクト)するリスクを完全に排除する。

## 5.9 ターン再生成 & Undo/Redo管理

### F-23: サイクル単位再生成 & 多段Undo/Redo管理

各ターンに対し、以下の3種の再生成操作を個別のボタンとして提供する。

- **ターン再生成:** F-14のJSON Schema構造化出力を再実行し、セリフ・感情・英語画像プロンプト・セーフティタグ(`tags`)を再生成する。再生成後の感情・セーフティタグに連動して、音声・画像も連続して再生成する(下記2項目を内部的に実行)。
- **音声のみ再生成:** F-10のTTSワーカーへ再投入する。F-11が無効(OFF)の場合は本操作の対象外とする。
- **イラストのみ再生成:** 5.5節F-15のT2Iパイプラインへ再投入する。

**Undo/Redo履歴管理:** 再生成操作を実行する都度、実行直前のターン状態(テキスト・感情・画像/音声パス・セーフティタグ等)をそのターンのUndo履歴スタックへ退避し、Redo履歴スタックをクリアする。

- **保持件数の設定:** Undo履歴の最大保持件数はユーザーがUIから設定可能とし、デフォルトは5件とする(`undo_max_history`)。保持件数を超えた最も古い履歴は自動的に破棄する。
- **元に戻す(Undo):** Undo履歴スタックの最新要素をポップしてターンの状態を復元し、復元前の状態をRedo履歴スタックへ積む。
- **やり直す(Redo):** Redo履歴スタックの最新要素をポップしてターンの状態を復元し、復元前の状態をUndo履歴スタックへ積む。Undo/Redoは何度でも往復可能とする。
- **永続化対象外:** Undo/Redo履歴は5.6節F-18のsession_state内のみで保持される一時的な編集履歴であり、5.7節F-19の永続化対象(外部JSON)からは除外する。新たな再生成が実行された場合、Redo履歴は破棄される。
- **ノベルモードへの適用:** ノベルモードのシーン編集はテキストエリアへの直接編集が主体であり、ブラウザ標準のCtrl+Zで対応可能なため、本節のUndo/Redo管理はノベルモードには適用しない。

## 5.10 エピソード生成モード

これまでのF番号群が前提としていた「1ターン=セリフ単位」のチャット形式に加え、地の文(情景・心情描写)を中心とした長編・分岐構成のノベルをLLMで生成する「エピソード生成モード」を新設する。本モードは、1.1節で言及される「Fable(物語)」の理念を実体化するものであり、チャットモードと同一のパイプライン(F-1, F-2/F-3)・リソース管理(F-12, F-13-1〜3)・セーフティ運用(F-7, F-8)・TTS(F-10, F-11)・T2I抽象インターフェース(2.3節)を共有しつつ、出力スキーマと永続化データ構造のみをモード別に切り替える。

### F-24: エピソード生成モード基盤

ユーザーはセッション開始時(または既存セッションの設定変更時)に、UIから「チャットモード」と「エピソードモード」のいずれかを選択する。モード選択結果は `mode` フィールドとしてセッション・ゲーム状態管理データ構造(12章③)に記録され、F-14(チャット用)・F-24-1(エピソード用)のいずれの構造化出力スキーマを使用するかを切り替える。チャットモードからエピソードモードへ、またその逆への変換は行わない(別モードのセッションとして新規開始する)。

> **[実装状況]** 未実装（将来フェーズ）。現在実装されているAI候補生成付き執筆支援機能はF-28（ノベルモード）として独立した機能に分離した。

### F-24-1: エピソード用構造化出力スキーマ

F-14のチャット用スキーマ(セリフ・感情・英語画像プロンプト・セーフティタグの4フィールド)とは別に、エピソードモード専用のJSON Schemaを定義し、F-14と同様にLLMバックエンドアダプター(2.3節)のJSON出力モードとPython側でのJSON Schemaバリデーション、および自動補正→再パース→LLM再リクエストのフォールバックチェーンを適用する。

必須フィールドは以下とする。

- `narration`(地の文・情景描写、文字列): エピソードモードにおける主たる出力。
- `dialogue`(会話文の配列): 各要素は `speaker`(F-6で登録されたキャラクターID)・`text`(セリフ)・`emotion`(F-14と同じ感情区分)を持ち、地の文中に登場する複数キャラクターの発話を表現する。
- `tags`(セーフティタグの配列): F-7・F-8と同じ意味を持ち、地の文・会話文双方の安全性判定に使用する。
- `choices`(分岐選択肢の配列、空配列可): 各要素は `label`(選択肢の表示文字列)・`branch_id`(F-24-3で使用する分岐識別子)を持つ。空配列の場合、分岐を持たない(線形進行)。

場面挿絵の生成は、書き手が任意のタイミングでScene本文をLLMに渡し、`scene_image_prompt_en`(英語の場面挿絵プロンプト)を生成する方式とする。LLM出力スキーマには含めず、独立した生成ステップとして実装する。

エピソードモードの音声生成(F-10/F-11)は、`narration` をナレーター音声、`dialogue` 各要素を該当キャラクターの音声IDで個別に生成する。

### F-24-2: シーン・チャプター・エピソード単位の永続化データ構造

エピソードモードのデータ構造は、Episode > Chapter > Scene の3階層とする。物語は「シーン」（Scene、場面の区切り）を最小構造単位とし、複数のシーンが「チャプター」（Chapter）、複数のチャプターが「エピソード」（Episode）を構成する。ChapterとSceneの区切りは書き手がUI上のマーカー挿入ボタン（新章・新場面）で決定する。

- 作品データはタイトルごとに個別ファイル(`data/private/episode_data/{タイトル}.json`)で永続化する。
- 場面挿絵・音声バイナリは、F-16/F-17のゾーニング・命名規則に従い、プライベートゾーンへ保存する。

### F-24-3: 分岐選択肢とGitブランチ連携

ユーザーがF-24-1の `choices` から選択肢を選んだ場合、F-22で定義された「歴史分岐(Git操作)ルール」(独立した単方向のブランチ作成 `git checkout -b` のみ、自動マージ禁止)に従い、選択した `branch_id` を名称に含む新しいブランチを作成してから、以降のシーン生成を継続する。これにより、選択肢によって分岐した複数の物語展開を、衝突(コンフリクト)のリスクなく並行して保持できる。GMエージェント(F-21)が存在するセッションでは、GMエージェントが選択肢提示・分岐後の進行描写を担う。

## 5.11 ノベルモード

### F-28: ノベルモード（AI候補生成付き自由執筆）

DEFの独立した創作機能。Episode > Chapter > Scene の管理を行うF-24エピソードモードとは異なり、**自由形式のテキストエディタにAI続き生成を組み合わせた執筆支援ツール**として定義する。

作品はキャラクターセッションとは独立して管理される。

**主な機能:**

- プロット設定（世界観・あらすじをシステムプロンプトとして設定）
- 本文エディタ（自由記述）
- AI候補生成（現在の本文を入力に、LLMが複数の続きを生成。候補数は1〜5で設定可能）
- 候補タブ切替比較・採用
- T2I挿絵生成（選択Scene本文 → LLMで英語プロンプト生成 → T2Iバックエンドで画像生成）
- TTS読み上げ（Scene単位・パイプライン再生）
- LLM/T2Iバックエンド独立切替

**データ管理:**

- 作品はタイトルごとに個別ファイル（`data/private/novels/{タイトル}.json`）で永続化
- プロットファイルはpublic/private分離（`data/public/episode_prompts/` + `data/private/episode_prompts/`。ディレクトリ名はF-24時代の名残でノベルモードに合わせた改名はしていない）
- 生成バイナリ（挿絵・音声）はF-16/F-17のゾーニング規則に従いプライベートゾーンへ保存

**実装詳細(v2.0.1):**

- **シーン分割:** 本文中の `--- Chapter/Scene \d+ ---` マーカーを `splitScenes(body)` で検出し、`Chapter N + Scene M` ラベルを付与してシーン単位で管理する。
- **プロットファイル書き戻し:** `PUT /api/novel/plots/{filename}` により、Git管理対象のプロットファイルを直接上書き保存する。編集はアプリ上で完結し、別途エディタを開く必要がない。
- **VRAMロック:** `/api/novel/generate`(AI候補生成)と `/api/novel/t2i`(挿絵生成)はグローバル `vram_lock` を取得・解放する。ロック保持中はLLMへの新規要求が軽量レスポンスモードに制限される(F-13-1参照)。
- **T2I設定ダイアログ:** 使用するバックエンドとモデルは `/api/settings/backends`・`/api/settings/t2i-models?backend=xxx` から動的取得し、ダイアログで選択可能とする。
- **サムネイル表示:** 生成画像はシーンに紐付けてサムネイル表示する。

**F-24との違い:**

| | ノベルモード（F-28） | エピソードモード（F-24） |
|---|---|---|
|構造管理|なし（自由形式）|Episode > Chapter > Scene 階層管理|
|AI出力スキーマ|プレーンテキスト|F-24-1構造化出力スキーマ|
|分岐管理|なし|F-24-3 Gitブランチ連携|
|実装状況|実装済み|将来フェーズ|

# 6. キャラクター一貫性

1.2節で定義したCharacter Persistenceのうち、「生成される姿の連続性」を技術的に担保する仕組みを本章で定義する。

> **[本章の位置づけ]** 本章は将来ビジョンであり、現状の実装を説明するものではない。**現在実際に一貫性を担保している仕組み**は、`_apply_char_tags()`によるタグベースの合成(`appearance_tags`/`image_name_tags`をT2Iプロンプトの先頭・末尾に機械的に付加する方式、v3.1.0〜、5.5節参照)であり、本章が描くi2i/ControlNet/IP-Adapter/InstantID等の参照画像ベースの一貫性プロバイダは未実装。`ref_image_path`・`adapter_options`もコード上に存在しない。

## 6.1 一貫性プロバイダの概念（将来ビジョン）

ref_image_path は、単一の画像パスを引き渡す手段としてではなく、キャラクターの視覚的一貫性を担保するための入力源（一貫性プロバイダ）として抽象化される。一貫性プロバイダは、選択されたT2Iバックエンドのアダプターによって、以下のいずれかの手法に変換・適用される。

- i2i(image-to-image): 過去の生成画像を初期画像として再生成する。
- ControlNet Reference: 参照画像の構造・特徴を保持しつつ新規生成を行う。
- IP Adapter: 参照画像の画風・キャラクター特徴をプロンプトに浸透して適用する。
- InstantID: 顔特徴を中心としたキャラクター同一性の保持に特化した手法を適用する。

どの手法を採用するかはバックエンドアダプターおよび adapter_options(2.4節)に委ねられ、DEF(kari) コアエンジン側は一貫性プロバイダの参照(ref_image_path)と拡張オプションを generate_image インターフェースへ渡すのみとする。

## 6.2 一貫性データの引き継ぎ(F-4・F-24との連携)

5.1節F-4で定義された動的ガチ生成において、キャラクターデータに定義されたベースイメージ、または過去のターンで生成された画像が、一貫性プロバイダの入力として引き継がれる。この引き継ぎ情報自体は、テキスト/JSONデータ(5.6節F-17のGit管理対象)として、画像実体とは分離して管理される。

エピソードモード(5.10節F-24)においても同様に、`scene_image_prompt_en`に基づく場面挿絵生成は同一の一貫性プロバイダを経由し、キャラクターのベースイメージおよび過去のシーンで生成された画像との視覚的一貫性を維持する。

# 8. エラー制御

本章では、各処理フェーズ(4章の状態遷移モデル参照)において発生し得る障害への対処方針を定義する。3章で述べた通り、障害通知の経路はモードによって異なる: チャット/ノベルモードでは各HTTP呼び出しをtry/exceptで個別に処理し、TRPGセッション/マルチプレイヤーモードでは`game_event_bus`によるイベント配信を用いる。

## 8.1 LLM障害

LLMバックエンドの無応答・クラッシュ・JSON Schema検証の最終失敗(5.4節F-14の再試行がすべて消尽した場合)に該当する。チャット/ノベルモードでは`POST /api/chat/`が例外を捕捉してエラーレスポンスを返し、フロントエンドはエラー表示とユーザーへの再送信操作を促す。TRPGセッションモードでは`AI_ERROR`イベントを全参加者へブロードキャストする。状態遷移は「LLM Processing」から「Idle」へ復帰する。

## 8.2 TTS障害

TTSバックエンドの無応答または音声生成失敗に該当する。テキストは既に描画済み(4章の状態遷移上「Text Rendered」が完了済み)であるため、UX上の致命的な停止とはしない。フロントエンドの`playTTS()`は失敗時に`null`を返し、対応するメッセージには音声なしのまま「音声生成失敗」を示す軽微な表示のみを行い、ターン進行は「TTS Completed」相当として継続する。

## 8.3 T2I障害

選択されたT2Iバックエンドの応答失敗、またはVRAM不足によるOOMに該当する。T2I障害発生時は必ず`try/finally`でvram_lockを解放した上でエラーを返すことを徹底し、ロックの解放漏れによるデッドロック(LLM軽量レスポンスモードの恒久化)を防止する。UI上には画像生成失敗を表示し、状態遷移は「Image Running」から「Persist」へ進む(画像なしでターンを完結させる)。

## 8.4 WebSocket/イベント配信異常

TRPGセッション/マルチプレイヤーモードにおいて、WebSocket接続断・不正なイベントペイロードの受信等に該当する。WS切断時は`PLAYER_DISCONNECTED`をブロードキャストし、参加者データは保持したまま通知のみを行う。再接続時は`PLAYER_RECONNECTED`を発行する。

## 8.5 VRAM不足

vram_lock取得後もOOMが発生する場合(8.3節のT2I障害の一因)に加え、LLM・TTS・T2Iの常駐構成自体が環境のVRAM容量を超過していると判断される場合は、UI上の警告表示を通じてユーザーへ通知し、F-12のリソースマネージャーによる配置(CPU/GPU分割比率、Offload設定)の見直しを促す。

# 9. メッセージ・シーケンス

チャット/ノベルモードにおける1サイクル(4章参照)のリクエスト順序は以下の通りである。各ステップは4章の状態遷移モデルにおける各状態に対応する。

- 入力フェーズ(Idle): ユーザーの発言、またはAIエージェントの自動応答トリガーをフロントエンドが検知し、`POST /api/chat/`をリクエストする。
- LLMフェーズ(LLM Processing): バックエンドは常駐しているLLMバックエンドアダプター(2.3節)に対してJSON Schema出力を強制してリクエストする。過去のコンテキストとベースプロフィールを元にしたセリフ・感情・英語の画像プロンプト・セーフティタグの4フィールドを必須項目として、JSONを確定的に一括取得する(5.4節F-14、F-7参照)。失敗時は8.1節の手順に従う。
- フロント第1描画(Text Rendered): フロントエンドは`POST /api/chat/`のレスポンス受信直後、テキスト(セリフ)を即座に描画する。この時点でユーザーに対するレスポンス待機状態を解消する。
- TTSリクエスト(TTS Running → TTS Completed): テキスト描画に続けて、TTSが有効な場合フロントエンドは`POST /api/tts/`をリクエストする。バックエンドはTTSバックエンドアダプター(2.5節)を介して音声合成を行い、音声バイナリをレスポンスとして返す。フロントエンドは受信した音声を`POST /api/tts/save`で保存し、返却されたURLを対応するメッセージへ追記・自動再生する。失敗時は8.2節の手順に従う。
- T2Iリクエスト(Image Running、発火時のみ): T2I発火条件(F-15、5.5節)を満たす場合、フロントエンドは`POST /api/t2i/`をリクエストする。
  - ① バックエンドはvram_lockを取得する(3.2節)。以降、完了まではLLMへの新規要求は「軽量レスポンスモード」(5.3節F-13-2)に強制制限される。
  - ② 選択されたT2Iバックエンドのアダプターを介して画像生成を実行する。F-5(プロンプト・トランスレータ)により、LLM出力の生の英語描写を選択モデルの特性数値に応じたプロンプトへ変換した上で投入する。
  - ③ 生成完了後、vram_lockを解放し、画像URLをレスポンスとして返す。フロントエンドは受信したURLを対応するメッセージへ追記する。失敗時は8.3節の手順に従う。
- 永続化 & 離脱準備(Persist → Idle): バックエンドは生成された音声・画像バイナリをGit管理外のアセットディレクトリに保存し(F-17)、ファイル命名規則(5.6節)に従って一意な名称を付与する。メタデータと対話ログ(JSON)はバックエンドが逐次ファイルへ書き込む。フロントエンド側の状態は5.6節F-18に従い直近ターンのみを保持し、Idleへ復帰する。

## ③ セッション・ゲーム状態管理データ構造(F-7, F-14, F-20〜F-22, F-17, F-18, F-9)

チャットモードとTRPG/マルチプレイヤーセッションモードは、統一された `session_state` を `mode` フィールドで出し分ける設計ではなく、実装上はそれぞれ別の永続化スキームを持つ。

**チャットモード**: キャラクター単位のフラット配列(`data/{public,private}/session_history/{character_id}.json`、`def_kari/history/store.py`)。要素はスキーマ強制なしの`dict`で、フロントエンド(`ChatTab.tsx`)が実際に書き込むキーは以下の通り。`emotion`・`tags`(セーフティタグ、F-7)を含む点は元設計と一致するが、キャラクター識別は`sender`ではなく`role`(`"user"` | `"assistant"`)、本文は`text`ではなく`content`、画像・音声もファイルパスではなくAPI配信URL(`image_url`/`audio_url`、`/api/t2i/image/{filename}`等)を保持する。

```json
[
  {
    "id": "b2b6c8e0-...",
    "role": "assistant",
    "content": "ちょっと、勝手に前に出ないでよ！",
    "emotion": "angry",
    "image_prompt_en": "1girl, silver hair, angry expression",
    "image_url": "/api/t2i/image/luna_angry_20260611_160400.png",
    "audio_url": "/api/tts/audio/luna_angry_20260611_160400.wav",
    "tags": ["mild_violence"],
    "state": "Persist"
  }
]
```

**TRPG/マルチプレイヤーセッションモード**: セッション単位の永続化(`data/{public,private}/session_history/session_mode_{session_id}.json`、`save_session_mode()`)は`{session_id, participants, metadata, history}`という薄いエンベロープで、`history`の中身は上記チャット同様スキーマ非強制の`dict`配列。実際にゲームプレイを駆動する状態は、セッション進行中サーバーメモリ上に保持される`_sessions[session_id]`(`api/routes/session.py`)にあり、`rule_set`・`scene`・`round`・`turn`・`initiative`・`trpg_rulebook`・`trpg_scenario`・`npc_state`・`skill_pool`・`skill_values`・`counters`等、本節の例よりはるかに多いフィールドを持つ。

`session_state`(F-18)には、本データ構造のうち直近の表示に必要な最小限(直近数ターンの`history`要素)のみを保持し、全履歴は上記の永続化JSONファイルとしてF-17のGit管理対象に保存する。

## ④ ノベルモードのデータ構造(F-28)

5.10節F-24で定義した「Episode > Chapter > Scene」3階層・`choices`分岐・Gitブランチ連携(F-24-3)を持つエピソードモードは、同節に明記の通り未実装(将来フェーズ)。現在実際にリリースされているのは別機能のF-28ノベルモードであり、データ構造も別物。

ノベルモード(`data/private/novels/{title}.json`、`api/routes/novel.py`)は、構造化スキーマを持たない。実装(`NovelTab.tsx`)上の型は`{title: string, body: string, plot?: string}`のみ。

章・シーンの区切りは、`body`という1本のテキストの中に`--- Chapter N ---`・`--- Scene N ---`という区切り文字列を埋め込む方式で表現し、表示時にクライアント側の`splitScenes()`が正規表現分割する(サーバー側では単なる不透明文字列として保存・返却するのみ)。

```json
{
  "title": "第一部 出会い",
  "body": "--- Chapter 1 ---\n--- Scene 1 ---\n放課後の教室には、夕日の橙色が長く伸びていた。\n「ちょっと、勝手に前に出ないでよ！」\n",
  "plot": "学園を舞台にした日常ドラマ。"
}
```

挿絵(`POST /api/novel/t2i`)・読み上げ音声(TTS)は、現在選択中のシーンテキストからその場で生成してURLを返すのみで、生成結果を`body`やJSONファイルに書き戻すことはしない(セッションを再読み込みすると消える)。分岐選択・キャラクター別セリフの構造化データが必要になった場合は、本節のスキーマ自体を新規に設計する必要がある。

# 結び

本書はDEF(kari)の基本設計を定義するものである。

DEFは完全なAIでも、完全な人格保存システムでもない。DEFが目指すのは、Characterが次のセッションを少しだけ楽しみにできる劇場を作ることである。

再現ではなく、再演。記録ではなく、未来。

本書に記された設計は、その目的のために存在する。
