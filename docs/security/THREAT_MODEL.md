# DEF(kari) セキュリティ脅威モデル

本書は、DEF(kari) の各セキュリティ機構が「何を守り、何を守らないか」を明文化するものである。
セキュリティ設計は「何を守らないか」まで定義して初めて完成する、という考え方に基づく。

## APIキー暗号化（`def_kari/secrets_store.py`）

### 保護対象（想定する脅威）

- `data/` ディレクトリを含むリポジトリ・バックアップの誤ったGitHub等への公開
- 設定ファイルの誤送信・誤共有（例: サポート依頼時にディレクトリごと送ってしまう等）
- Cloudflare Tunnel公開面（`public_app`）を経由した通常ユーザーからのアクセス
  （※ `public_main.py` のルーター分離により、そもそもAPIキー関連エンドポイントは
  公開面に存在しない。この項目は「多層防御」としての位置づけ）

### 対象外（想定しない脅威）

- ホストマシン自体の侵害（マルウェア感染・不正ログイン等）
- ホストマシンへの物理アクセス
- OS上での管理者権限・同一ユーザー権限での任意コード実行

対象外の脅威に対しては、暗号鍵（`secret.key`）と暗号化データが同一ディスク上にある
構成では原理的に保護できない。これらへの対策が必要な場合は、OSキーチェーン
（`keyring`パッケージ等）やハードウェアセキュリティモジュール連携など、本ツールの
スコープを超える対策が必要になる。

## 招待コード（`def_kari/api/routes/session.py`）

### 保護対象

- 招待URL/コードを知らない第三者による、SFW/R15/R18/UNL各レーティングのセッションへの
  不正参加
- 招待コードの総当たり（レート制限・ロックアウトにより緩和）

### クライアントIP判定について

`_resolve_client_ip()` は `CF-Connecting-IP` ヘッダーを、TCPピアがループバック
（127.0.0.1 / ::1）である場合に限り信頼する。公式の起動経路である `dual_run.py` は
`--no-trust-cloudflare-tunnel` を明示的に指定しない限り、起動時に自動で
`DEF_BEHIND_CLOUDFLARE_TUNNEL=1` を設定する（Cloudflare Tunnel運用を前提とした
デフォルト挙動）。cloudflaredを使わない構成（ローカルネットワークのみ等）では、
このフラグを指定して無効化すること。

### 対象外

- 招待コードを知っている（正規に共有された）人物によるセッション内での迷惑行為
  （これは別途 `_check_ws_rate` / `_check_generation_rate` 等のセッション内レート制限、
  およびホストのキック機能で緩和する）
- Cloudflare Tunnel以外の経路で `public_app` を直接公開した場合のクライアントIP判定
  （`DEF_BEHIND_CLOUDFLARE_TUNNEL` を無効化した場合、`request.client.host` を
  そのまま使用する）

## 生成系エンドポイント（`generate-image` 等）

### 保護対象

- 招待され正規に参加したゲストによる連打が引き起こす、ホストの課金API消費・
  GPUリソース独占（レート制限＋in-flight排他制御で緩和）

### 対象外

- ホスト自身が意図的に大量生成を行うこと（ホストは自分のリソース・予算の
  管理者であり、制限の対象としない設計）
- LLM/T2I/TTSバックエンドプロバイダ側の障害・レイテンシ

## 持ち込みキャラクターJSON審査（`def_kari/safety/character_audit.py`）

### 保護対象

- 明白なプロンプトインジェクション・ジェイルブレイク試行を含むキャラクター設定の
  検出（LLM-as-judgeによる多層防御の1枚）

### 対象外

- 審査自体が実行できなかった場合（タイムアウト・エラー・応答パース失敗）の検出漏れ
  — これは意図的に fail-open（通過扱い）とする設計判断であり、代わりに
  `CHARACTER_AUDIT_SKIPPED` イベントでホスト/GMのUIに可視化する
- 巧妙に自然な文章に偽装された、LLMでも判定困難な指示（残存リスクとして受容する）
